# i18n — Guia para novas páginas (issue #12)

Como funciona a troca de idioma no NecroForja e o que fazer para que **toda página nova** já nasça compatível.

## Modelo

- **Biblioteca**: [next-intl](https://next-intl.dev) v4, **sem routing de URL** (não existe `/pt-BR/...`).
- **Locales**: `en` (padrão) e `pt-BR`. Fonte única: `src/i18n/config.ts`.
- **Seleção**: exclusivamente pelo cookie `NEXT_LOCALE`, gravado pelo `<LocaleSwitcher />` (botão EN/PT no `SiteNav`). **Sem cookie ⇒ inglês. Não há detecção de navegador — e não deve haver.**
- **Provider**: `NextIntlClientProvider` já está no layout raiz (`src/app/layout.tsx`). Qualquer página/componente novo tem acesso a `useTranslations()` e `useLocale()` sem configuração extra — funcionam em **server e client components**.

## Regras de ouro

1. **Banco de dados, lógica, enums, IDs, chaves e códigos de erro: sempre em inglês.**
   O pt-BR é uma camada de exibição, nada além disso. Exemplo: a action de login retorna o código `invalid_credentials`; o front traduz via `t("errors.invalid_credentials")`.
2. **IDs estáveis em inglês como chave de tradução.** Cards de gangue usam `t(\`cards.${g.id}.desc\`)` com `GH-01` etc. Isso mantém busca/lógica independente de idioma (importante para o search global futuro: indexar por chave canônica, exibir por locale).
3. **Metadata (`title`, `description`, OG) estática em inglês.** Crawlers não têm cookie; não fazer metadata dependente de locale.
4. **Não traduzir**: nomes canônicos do jogo (House Escher, Ash Wastes, Bottle out, Priority...), IDs de âncora (`#anatomia`), classes CSS, notação de dados/dice, números.
5. **Página que lê locale vira rota dinâmica** (cookie), sem ISR. Foi o caso da landing. É esperado.

## Padrão A — strings de UI (títulos, botões, labels)

Adicionar um namespace em **ambos** os arquivos `messages/en.json` e `messages/pt-BR.json`:

```json
// messages/en.json
"MinhaPage": { "title": "My Title", "cta": "GO →" }
```

```tsx
import { useTranslations } from "next-intl";

export default function MinhaPage() {
  const t = useTranslations("MinhaPage");
  return <h1>{t("title")}</h1>;
}
```

Arrays: `t.raw("items") as string[]` (ver `Ticker.tsx`).

## Padrão B — conteúdo pesado/estruturado (tipo lore)

Para páginas com muito texto estruturado (capítulos, checklists), não usar JSON:

- `content.ts` — fonte da verdade em PT-BR (nunca reescrever o texto existente).
- `content.en.ts` — espelho traduzido; mesma estrutura, mesmos ids/cores/srcs; importa os types de `./content`.
- `content.i18n.ts` — seletor: `getXContent(locale: Locale)`.

Na página (server): `const locale = await getLocale()` (de `next-intl/server`) → `getXContent(locale)`. Em client components: `useLocale()`.

Strings soltas de componente podem usar um record local:

```tsx
const STRINGS: Record<Locale, { back: string }> = {
  en: { back: "← BACK" },
  "pt-BR": { back: "← VOLTAR" },
};
```

## Padrão C — seletor de idioma na página

Se a página usa `<SiteNav />`, o seletor já vem junto. Se tiver header próprio (dashboard, admin), incluir `<LocaleSwitcher />` (`src/components/LocaleSwitcher.tsx`).

## Checklist para nova página

- [ ] Nenhuma string visível hardcoded — tudo via Padrão A ou B
- [ ] Chaves/IDs/lógica/dados em inglês; tradução só na exibição
- [ ] Metadata estática em inglês
- [ ] Namespace criado nos **dois** `messages/*.json` (chaves idênticas)
- [ ] Testar com e sem `Cookie: NEXT_LOCALE=pt-BR`
- [ ] `npm run typecheck && npm run lint`
